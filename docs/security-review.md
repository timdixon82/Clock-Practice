## OWASP Top 10 Assessment

The OWASP (Open Worldwide Application Security Project) Top 10 is the standard list of the ten most critical web application security risks. Each item is assessed below against this project's architecture: a single-page static site of HTML, CSS, and JavaScript, with no server, no database, and no authentication system.

### A01: Broken Access Control

Not applicable. There is no server-side access control because there is no server. The site has no login, no user accounts, and no privileged pages. All content is equally public. The only access control in scope is the GitHub repository access control, which is managed at the platform level and is outside this site's code.

### A02: Cryptographic Failures

Not applicable. No sensitive data is processed, stored, or transmitted. There are no passwords, tokens, payment details, or personal data of any kind in this application. Transport encryption is provided by HTTPS, which is enforced by the GitHub Pages configuration (see the GitHub Pages section below).

### A03: Injection

Substantially not applicable, with one note. There is no server, no database, and no template engine, so SQL injection, command injection, and server-side template injection cannot occur. The JavaScript in `index.html` does use `innerHTML` in one location: the success feedback panel in the `checkAnswer` function. The values written there are `currentHour` and `currentMinute`, which are integers generated by `Math.random()` internally and are never derived from any user-supplied string. The `attempts` counter is a JavaScript integer incremented by the application. No user-controlled string is ever interpolated into `innerHTML`. The injection risk from this pattern is therefore assessed as negligible for this specific code, and Jed's code review will confirm or qualify this at the implementation level.

### A04: Insecure Design

Low residual risk. The application is a game with no authentication, no payment flow, and no sensitive workflow. The only design-level concern is the share feature, which generates a canvas image and invokes the browser's native Web Share API (Application Programming Interface). No data is sent to a third-party server; the share action is handled entirely by the operating system's native sharing sheet. This is an appropriate design for a public, data-free application.

### A05: Security Misconfiguration

Partially applicable. The application code itself has no configurable security settings to misconfigure. The risk sits at the platform level: GitHub Pages does not allow custom HTTP (Hypertext Transfer Protocol) response headers, so security headers such as Content-Security-Policy (CSP), Strict-Transport-Security (HSTS), X-Frame-Options, X-Content-Type-Options, and Permissions-Policy cannot be set directly. The mitigations for this constraint are described in the GitHub Pages section below. This is the principal security governance finding for this project.

### A06: Vulnerable and Outdated Components

Not applicable in the conventional sense. This project has no npm (Node Package Manager) dependencies, no third-party JavaScript libraries, and no build toolchain. The entire application is contained in two files: `index.html` and `favicon.svg`. There are no components to track for vulnerabilities.

### A07: Identification and Authentication Failures

Not applicable. There is no user authentication of any kind. The application is fully anonymous and public.

### A08: Software and Data Integrity Failures

Low residual risk. There is no Continuous Integration / Continuous Delivery (CI/CD) pipeline at present. Deployment is a direct push to GitHub Pages from the `main` branch. The risk of a compromised build pipeline injecting malicious code is therefore low, though the absence of any pipeline also means there is no automated integrity check on deploys. This is acceptable for the current project scale. If a CI/CD pipeline is introduced in future, subresource integrity checks and signed commits should be added.

### A09: Security Logging and Monitoring Failures

Partially applicable. The application does not log anything to a server because there is no server. GitHub Pages provides no server-side access logs accessible to the project owner. This means there is no visibility into traffic anomalies or attempted attacks. For a public, data-free, low-risk game this is acceptable. If the project ever handles personal data or adds server-side functionality, logging and alerting would become a firm requirement.

### A10: Server-Side Request Forgery (SSRF)

Not applicable. There is no server. The application makes no outbound network requests whatsoever. The share feature uses the browser's native Web Share API, which does not make HTTP requests on behalf of a server.

## UK GDPR Assessment

The UK GDPR (United Kingdom General Data Protection Regulation) applies to any processing of personal data relating to identifiable individuals. This section assesses whether the application processes any personal data.

### Forms

There are no forms that collect name, email address, date of birth, or any other personal identifier. The two inputs in the application (hour and minute spinners) accept only numeric values within fixed ranges and record only whether a user's answer matches a randomly generated time. No submission is made to any server.

### Analytics

No analytics script is present. There is no Google Analytics, Plausible, Fathom, Cloudflare Web Analytics, or any equivalent tracking code anywhere in `index.html`.

### Cookies

No cookies are set or read, either by the application code or by any third-party script. The application contains no cookie banner, cookie consent mechanism, or cookie declaration, which is correct given that no cookies are used.

### localStorage and sessionStorage

The application does not read from or write to `localStorage` or `sessionStorage`. No data of any kind is persisted between sessions.

### Third-Party Network Calls

The application makes no third-party network calls. There are no external fonts loaded from Google Fonts or any other host, no analytics beacons, no social media widgets, no CDN (Content Delivery Network) script tags, and no fetch or XMLHttpRequest calls in the JavaScript. The only external asset is the `favicon.svg`, which is served from the same origin.

### Web Share API

When a user taps the Share button, the browser's native Web Share API is invoked. The data passed to `navigator.share()` is: a title string ("Clock Practice - Got it right!"), a text string containing the solved time and attempt count (for example "I read the clock! It said 3:45 and I got it right in 2 tries!"), and optionally a canvas-generated PNG image of the clock. None of this data is collected by or transmitted to the project owner or any third party. The sharing destination is chosen entirely by the user on their own device. No personal data is processed on behalf of the project operator.

### UK GDPR Conclusion

This application does not process any personal data. No lawful basis is needed. No privacy notice is required. No data subject rights mechanisms are required. No data retention schedule is needed. The application is fully outside the scope of the UK GDPR as currently coded. This conclusion must be revisited if any of the following are added: analytics, cookies, a contact form, user accounts, server-side logging, or any third-party script.

## GitHub Pages Security Posture

### HTTPS Enforcement

HTTPS is enforced on the GitHub Pages site. This means all connections are encrypted in transit using Transport Layer Security (TLS). Requests to the plain HTTP (port 80) address are automatically redirected to HTTPS. This is the correct configuration and satisfies the A02 cryptographic transport requirement.

### No Server

GitHub Pages serves only static files. There is no application server, no database, no server-side scripting, and no execution environment. This eliminates a large class of server-side vulnerabilities, including SQL injection, remote code execution, SSRF, and broken authentication. The attack surface is limited to the browser-side code and the hosting platform itself.

### Security Response Headers: Constraint and Mitigations

GitHub Pages does not allow project owners to set custom HTTP response headers. This means the following headers, which are standard defences for web applications, cannot be set:

- Content-Security-Policy (CSP): restricts which scripts, styles, and other resources the browser is permitted to load.
- Strict-Transport-Security (HSTS): instructs the browser to always use HTTPS for this domain, even before the server responds.
- X-Frame-Options: prevents the page from being embedded in a frame on another origin.
- X-Content-Type-Options: prevents the browser from guessing the content type of a response.
- Permissions-Policy: restricts access to browser features such as the camera, microphone, and geolocation.

The practical impact of each missing header, given this application's characteristics, is as follows.

CSP is the most significant missing header. Without CSP, if a cross-site scripting (XSS) vulnerability were introduced in future code, the browser would not have a second line of defence to block script execution. The current code's low injection risk (assessed under A03 above) limits the practical exposure today, but this remains a standing governance concern for all future development on this project.

HSTS is partially mitigated by the GitHub Pages HTTPS enforcement, which handles the redirect. The risk of a user connecting over plain HTTP before the redirect happens is low but non-zero.

X-Frame-Options and X-Content-Type-Options carry low risk for this application because there is no sensitive content that could be exploited via clickjacking or MIME-type confusion.

Permissions-Policy is relevant because the Web Share API accesses device sharing capabilities. Without Permissions-Policy, a hypothetical malicious script could invoke broader browser APIs. The current application loads no third-party scripts, so the risk is low.

Recommended mitigations for the header constraint:

1. Include a `<meta http-equiv="Content-Security-Policy">` tag in `index.html`. The Meta element equivalent of CSP cannot enforce all directives (for example, it cannot set `frame-ancestors`), but it does restrict script and resource loading and is the best available mitigation for a GitHub Pages site. A suitable policy for this application would be a strict default-src of 'self', with script-src limited to 'self' and allowing only the inline script already present (using a nonce or hash, if the build allows it).
2. Submit the domain to the HSTS Preload list via [HSTS Preload Submission](https://hstspreload.org) once the project is on a custom domain. This bakes HSTS into browsers without requiring the header.
3. Accept the remaining header gaps as a documented exception, given the low sensitivity of this application and the platform constraint. See the exception record below.

### Exception: Security Response Headers Cannot Be Set on GitHub Pages

- Reference: SEC-001
- Date raised: 2026-05-21
- Raised by: Gerrie (security governance)
- Status: Pending Tim's approval

Reason: GitHub Pages does not support custom HTTP response headers. The headers Content-Security-Policy, Strict-Transport-Security, X-Frame-Options, X-Content-Type-Options, and Permissions-Policy cannot be set at the platform level.

Risk: Without these headers, there is no server-enforced second line of defence against cross-site scripting or clickjacking. The risk is assessed as low for this specific application because it processes no personal data, loads no third-party scripts, and contains no login or payment flows.

Mitigation: A `<meta http-equiv="Content-Security-Policy">` tag should be added to `index.html` to provide a browser-side policy. HTTPS enforcement is already in place. If the project moves to a custom domain, HSTS preload submission is recommended.
